Skopeo: design of a multi-agent repository risk analyst

Thirteen agents investigate a GitHub repository together: an orchestrator plans and re-plans, eight specialists gather evidence in parallel, and four coordination agents correlate, challenge, score and fix. They communicate through a shared Evidence Store (blackboard) and a persisted message log, and every decision is visible in the execution trace.

1. Architecture and data flow

How a request flows. The user submits a GitHub repository (or picks one after signing in with GitHub). The API validates it and opens a case. The Orchestrator profiles the repository and plans which specialists to run and why (it records a reason for every agent selected or skipped). LangGraph fans the tasks out with Send, so the specialists run in parallel; each posts findings, the evidence behind them, and requests for follow-up work to the Evidence Store. After every phase the orchestrator reviews the blackboard and decides the next step: dispatch more work (follow-ups, retries, benchmarks), correlate, verify, assess or finish. The Correlation agent links findings across specialists; the Red-Team agent challenges each finding and either verifies it, rejects it, or sends it back for more evidence; the Risk agent scores only verified findings; the Recommendation agent writes fixes and proposes GitHub actions that wait for human approval. After the case, the Ask-the-agents router sends each user question to the agent that owns the topic.

3. Orchestration pattern

Named pattern: hierarchical orchestrator–worker over a blackboard. The orchestrator issues AgentTasks (agent, objective, mode, strategy, focus, trigger, attempt, round); workers return TaskResults. Workers do not call each other: they publish to the Evidence Store, and later work is driven by what is on the board. That is how one agent's discovery changes another agent's task.

Why this pattern

  • Orchestrator–worker because the work needed is only known after the first round: a vulnerable library in the login path calls for three new tasks, a crashed agent for a degraded retry, an unmeasured performance claim for a benchmark. A fixed pipeline cannot express this.
  • Blackboard because thirteen agents passing results directly would need 156 pairwise channels; a single typed store gives every agent the same evidence, makes every write auditable, and lets an agent added later (the chat router) reuse all of it.
  • Adversarial verifier because the specialists' tools produce false positives; a separate agent whose only job is to disprove findings is what removes them before scoring.
  • Parallel fan-out because the specialists are independent; LangGraph Send runs eight at once, and the next review starts when the whole superstep completes.

Where the LLM decides, and how it is kept safe

Agents never call a model directly. They call LLMProvider.decide() with a Pydantic output schema, trusted structured state, repository text marked as untrusted, and a deterministic policy. The model's answer must validate against the schema and the agent's guardrails (for example, the orchestrator may only route to the five allowed steps; the red team may not reject a finding unless one of its checks failed; the chat may cite only finding ids that exist). If the model fails, times out, returns invalid output or the per-case call budget is spent, the policy decides and the trace records policy-fallback. Every decision records who made it (llm:<model> or policy), so the evaluator can see which decisions came from the model. The submitted trace was captured without a model key, so its decisions show policy; the deployed site runs the same graph with Groq.

5. Ask the agents (designated-agent answers)

After an investigation, a user can ask questions in the case's Ask the agents tab. The router scores the question against each agent's domain (and, with Groq, asks the fast model to choose, validated against the list of real agents). The chosen agent then answers only from what it recorded: its findings, their evidence and verification, and code excerpts from the clone. In the submitted trace, "What should I fix first?" went to the Recommendation agent, "Is the JWT handling safe?" to the Security agent, "Which findings did the red team reject?" to the Verification agent and a license question to the License agent, each answer citing real findings.

6. Input and output

Input (POST /api/investigations, schema InvestigationCreate): repository_url (https GitHub URL only), branch (validated ref, default main), analysis_depth (quick | standard | deep), enable_github_actions (bool). Unknown fields are rejected. Questions: POST /api/investigations/{id}/chat {"question", "agent"?}. Repository import after GitHub sign-in: POST /api/github/import.

Output (GET /api/investigations/{id}/report): status, overall risk, findings (with evidence ids, confidence factors and status), the red team's verifications, correlations, risks P0–P4, recommendations, action proposals, agent requests, a per-agent coverage table and the full event trace. Full schemas and real samples are in the submitted Input and Output Definitions.

7. Technology choices

ChoiceWhy
LangGraphAn explicit state machine with conditional edges (the orchestrator's routing), Send fan-out/fan-in for parallel specialists, reducers to merge parallel results, and recursion limits. We need the control flow to be decided at run time, which a chain or a no-code workflow tool cannot do.
Groq, openai/gpt-oss-120b for reasoningPlanning, review/routing, red-team judgements and chat answers need careful reasoning; Groq serves this open-weight model fast enough to keep a live case interactive, with JSON-mode structured output.
Groq, openai/gpt-oss-20b for fast tasksCorrelation assessment, code review summaries, recommendation wording and question routing are short, frequent calls where latency and rate limits matter more.
Provider abstraction + deterministic policiesOne interface for Groq, OpenAI, any OpenAI-compatible server, or no model at all; agents keep working (and stay testable) when the model is down or rate-limited.
FastAPI + Pydantic 2Typed schemas end to end; the same models validate API input and every LLM output.
SQLAlchemy 2 + Alembic; SQLite or PostgreSQLA real relational blackboard with migrations. SQLite needs no setup locally; PostgreSQL (free Neon) keeps data on hosts without a persistent disk.
Deterministic tools first (AST, OSV, pytest, coverage, git)Evidence comes from tools; the LLM judges and explains it, which keeps findings reproducible and checkable by the red team.
React + TypeScript + ViteA typed client mirroring the API: live trace, agent timeline, findings, rulings and chat.
Firebase AuthenticationGoogle and GitHub sign-in without storing passwords; the API verifies ID tokens itself.
Docker, Render, NeonOne container serves UI and API; free hosting with a free PostgreSQL database so data survives restarts.

8. Robustness and safety

SituationBehaviour
Invalid inputRejected with HTTP 422 before any agent runs (non-GitHub URL, bad branch, unknown field, invalid depth).
A specialist crashes or times outOnly that run fails; evidence already written is kept; siblings continue; retried once with a fallback strategy, then reported unavailable in the coverage table.
LLM unavailable, invalid or over budgetThe deterministic policy decides and the trace says so.
A claim cannot be settledIt stays "needs more evidence" and is excluded from the risk score.
Runaway investigationRound limits, per-agent iteration, tool-call and time budgets, a deadline guard that routes to assessment, a hard timeout; users can cancel.
Hostile repository contentTreated as data, never instructions; no shell, allowlisted argv commands with limits; untrusted code is not executed unless sandboxing is enabled; secrets redacted everywhere; GitHub actions need approval and DRY_RUN is on by default.
Server restartCases left running are marked interrupted; with PostgreSQL, accounts and cases persist.

9. Engineering practice

  • Structure: backend/app/{agents, graph, llm, chat, services, tools, security, api, models, schemas, watch, notifications}, frontend/src, examples/ (reference repository), docs/.
  • Tests: 209 automated tests (unit, integration, end-to-end API) covering agents, the full multi-agent run, fault isolation, verification, prompt injection, GitHub import, chat routing and the database; they pass on SQLite and PostgreSQL. CI runs lint, tests, the frontend build and a container smoke test.
  • Hygiene: no secrets in the repository (.env is ignored; keys come from the host), Ruff and ESLint clean, Alembic migrations for every schema change.

10. Limitations

  • Deep static analysis is Python-first; other languages get manifest, advisory, license and pattern coverage.
  • Test execution of real repositories requires sandboxed execution to be enabled; otherwise the test agent is static.
  • Reachability is import-graph based; dynamic imports can be missed (reported as inconclusive).
  • Without a model key the agents' judgement comes from transparent rule-based policies; the event flow and state transitions are the same.
