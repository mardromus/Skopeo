Multi-agent repository intelligence and risk analysis

Skopeo: design of a multi-agent repository risk analyst that proves what it finds

Thirteen agents investigate a GitHub repository together: an orchestrator plans and re-plans, eight specialists gather evidence in parallel, and four coordination agents correlate, challenge, score and fix. They communicate through a shared Evidence Store (a blackboard) and a persisted message log. Every claim cites its evidence, every finding is cross-examined by a red team, and nothing reaches GitHub without a human.

01Architecture and data flow

01IntakeValidate the URL, clone at a commit, record the guardrails.
02PlanProfile the repository; choose agents, with a reason for each.
03InvestigateEight specialists run in parallel and write evidence.
04CorrelateLink findings into compound risks and contradictions.
05Red teamChallenge every finding; verify, reject or ask for more.
06Score & actRank P0–P4; propose fixes that wait for approval.

The orchestrator reviews the blackboard after every phase, so steps 3–5 can repeat: follow-ups, retries and benchmarks are scheduled when the evidence calls for them.

How a request flows. The user submits a GitHub repository (or picks one after signing in with GitHub) and chooses the case's guardrails: dry run, whether approved actions may reach GitHub, and whether repository code may execute. The API validates the request and opens a case. The Orchestrator profiles the repository and plans which specialists to run and why (it records a reason for every agent selected or skipped). LangGraph fans the tasks out with Send, so the specialists run in parallel; each posts findings, the evidence behind them, and requests for follow-up work to the Evidence Store. After every phase the orchestrator reviews the blackboard and decides the next step: dispatch more work (follow-ups, retries, benchmarks), correlate, verify, assess or finish. The Correlation agent links findings across specialists; the Red-Team agent challenges each finding and either verifies it, rejects it, or sends it back for more evidence; the Risk agent scores only verified findings; the Recommendation agent writes fixes and proposes GitHub actions that wait for human approval. After the case, the Ask-the-agents router sends each user question to the agent that owns the topic.

03Orchestration pattern and messages

Named pattern: hierarchical orchestrator–worker over a blackboard. The orchestrator issues AgentTasks (agent, objective, mode, strategy, focus, trigger, attempt, round); workers return TaskResults. Workers do not call each other: they publish to the Evidence Store, and later work is driven by what is on the board. That is how one agent's discovery changes another agent's task.

Why orchestrator–worker

The work needed is only known after the first round: a vulnerable library in the login path calls for three new tasks, a crashed agent for a degraded retry, an unmeasured performance claim for a benchmark. A fixed pipeline cannot express this.

Why a blackboard

Thirteen agents passing results directly would need 156 pairwise channels. One typed store gives every agent the same evidence, makes every write auditable, and let a later agent (the chat router) reuse all of it.

Why an adversarial verifier

The specialists' tools produce false positives. A separate agent whose only job is to disprove findings removes them before scoring.

Why parallel fan-out

The specialists are independent; LangGraph Send runs eight at once, and the next review starts when the whole superstep completes.

Where the LLM decides, and how it is kept safe. Agents never call a model directly. They call LLMProvider.decide() with a Pydantic output schema, trusted structured state, repository text marked as untrusted, and a deterministic policy. The model's answer must validate against the schema and the agent's guardrails (the orchestrator may only route to the five allowed steps; the red team may not reject a finding unless one of its checks failed; the chat may cite only finding ids that exist). If the model fails, times out, returns invalid output or the per-case call budget is spent, the policy decides and the trace records policy-fallback. Every decision records who made it (llm:<model> or policy). The submitted trace was captured without a model key, so its decisions show policy; the deployed site runs the same graph with Groq.

05Ask the agents

After an investigation, a user can ask questions in the case's Ask the agents tab. The router scores the question against each agent's domain (and, with Groq, asks the fast model to choose, validated against the list of real agents). The chosen agent then answers only from what it recorded: its findings, their evidence and verification, and code excerpts from the clone. Every cited finding id is checked against the case before the answer is shown.

In the submitted trace, "What should I fix first?" went to the Recommendation agent, "Is the JWT handling safe?" to the Security agent, "Which findings did the red team reject?" to the Verification agent and a license question to the License agent, each answer citing real findings. Conversations are stored per user and per case.

06Human control and guardrails

Skopeo can act on GitHub and can, if allowed, run a repository's own tests. Both are off by default and both stay under the user's control at three levels.

Dry run · three levels

A personal default saved on the account (the dry run switch in the header); a choice in the pop-up shown before every case starts, from the home page or a GitHub import; and a switch on the case page that can be flipped while the case runs, which decides what the next approval does.

Named human approval

Recommended fixes become proposed GitHub issues and draft pull requests. Each needs a named approval; with dry run on the approval is recorded and nothing leaves the server. Skopeo never merges, deploys, deletes files or rotates credentials.

Code execution

Off by default: agents read code but never run it. Changing the setting asks for confirmation twice, and the server refuses it unless SKOPEO_ALLOW_CASE_EXECUTION is set, so a shared deployment cannot be made to run untrusted code.

Private repositories

Imported with the owner's GitHub token, which is stored encrypted (Fernet). Private cases are visible only to their owner; others receive 404.

07Upstream watches and notifications

A project is the user's own code: a GitHub repository or uploaded source files and manifests. A watch follows an open-source library that project depends on. On each check (hourly, daily, weekly or on demand) Skopeo diffs the library's public API between the version the project pins and the new release (removed and moved symbols, changed signatures, changed behaviour and contracts, additions) and maps every change to the call sites in the project.

ChannelDelivery
EmailSMTP, or HTTPS APIs (Brevo, Resend) on hosts that block SMTP ports; addresses are verified with a code
Slack, DiscordIncoming webhooks with formatted messages
WebhookJSON payload signed with HMAC-SHA256 (X-Skopeo-Signature), public destinations only

Rules choose which events reach which channel: case finished or failed, high-priority risk found, an upstream change that affects the project, a failed watch check. Every delivery is logged with its status.

08Input and output

Input (POST /api/investigations, schema InvestigationCreate): repository_url (https GitHub URL only), branch (validated ref, default main), analysis_depth (quick | standard | deep), enable_github_actions (bool), and optional per-case dry_run and sandbox_execution (null keeps the user's or server's default). Unknown fields are rejected. Related endpoints: questions POST /api/investigations/{id}/chat; switching dry run PATCH /api/investigations/{id}/options; personal defaults PUT /api/auth/preferences; repository import POST /api/github/import.

Output (GET /api/investigations/{id}/report, also as Markdown): status, overall risk, findings (with evidence ids, confidence factors and status), the red team's verifications, correlations, risks P0–P4, recommendations, action proposals, agent requests, a per-agent coverage table and the full event trace. Full schemas and real samples are in the submitted Input and Output Definitions.

09Technology choices

ChoiceWhy
LangGraphAn explicit state machine with conditional edges (the orchestrator's routing), Send fan-out/fan-in for parallel specialists, reducers to merge parallel results, and recursion limits. The control flow is decided at run time, which a chain or a no-code workflow tool cannot do.
Groq, openai/gpt-oss-120b for reasoningPlanning, review/routing, red-team judgements and chat answers need careful reasoning; Groq serves this open-weight model fast enough to keep a live case interactive, with JSON-mode structured output.
Groq, openai/gpt-oss-20b for fast tasksCorrelation assessment, code review summaries, recommendation wording and question routing are short, frequent calls where latency and rate limits matter more.
Provider abstraction + deterministic policiesOne interface for Groq, OpenAI, any OpenAI-compatible server, or no model at all; agents keep working (and stay testable) when the model is down or rate-limited.
FastAPI + Pydantic 2Typed schemas end to end; the same models validate API input and every LLM output.
SQLAlchemy 2 + Alembic; SQLite or PostgreSQLA real relational blackboard with migrations. SQLite needs no setup locally; PostgreSQL (free Neon) keeps data on hosts without a persistent disk.
Deterministic tools first (AST, OSV, pytest, coverage, git)Evidence comes from tools; the LLM judges and explains it, which keeps findings reproducible and checkable by the red team.
React + TypeScript + ViteA typed client mirroring the API: live trace, agent timeline, findings, rulings, chat, projects and notifications, in light and dark themes.
Firebase AuthenticationGoogle and GitHub sign-in without storing passwords; the API verifies ID tokens itself, with no service account.
Docker, Render, NeonOne container serves UI and API; free hosting with a free PostgreSQL database so data survives restarts.

10Robustness and safety

SituationBehaviour
Invalid inputRejected with HTTP 422 before any agent runs (non-GitHub URL, bad branch, unknown field, invalid depth).
A specialist crashes or times outOnly that run fails; evidence already written is kept; siblings continue; retried once with a fallback strategy, then reported unavailable in the coverage table.
LLM unavailable, invalid or over budgetThe deterministic policy decides and the trace says so.
A claim cannot be settledIt stays "needs more evidence" and is excluded from the risk score.
Runaway investigationRound limits, per-agent iteration, tool-call and time budgets, a deadline guard that routes to assessment, a hard timeout; users can cancel.
Hostile repository contentTreated as data, never instructions; no shell, allowlisted argv commands with limits and a stripped environment; untrusted code is not executed unless execution is allowed and chosen; secrets redacted everywhere.
Outbound actionsGitHub actions need a named approval and respect dry run; webhooks are restricted to public destinations; credentials and tokens never appear in logs or error messages.
Abuse of a public deploymentOptional access key for scans, per-client rate limits, a strict Content-Security-Policy, owner-only private cases.
Server restartCases left running are marked interrupted; with PostgreSQL, accounts, cases, projects and watches persist.

12Engineering practice and limitations

Structure

backend/app/{agents, graph, llm, chat, services, tools, security, api, models, schemas, watch, notifications}, frontend/src, examples/ (reference repository), docs/.

Tests

221 automated tests (unit, integration, end-to-end API): agents, the full multi-agent run, fault isolation, verification, prompt injection, GitHub import, chat routing, case options, email delivery and the database. They pass on SQLite and PostgreSQL.

Hygiene

No secrets in the repository (keys come from the host), Ruff and ESLint clean, TypeScript strict, an Alembic migration for every schema change.

Limitations

  • Deep static analysis is Python-first; other languages get manifest, advisory, license and pattern coverage.
  • Test execution of real repositories requires execution to be allowed and chosen; otherwise the test agent is static.
  • Reachability is import-graph based; dynamic imports can be missed (reported as inconclusive).
  • Without a model key the agents' judgement comes from transparent rule-based policies; the event flow and state transitions are the same.
  • The free Render plan sleeps after 15 minutes without traffic, so the first request after a pause waits about a minute.
